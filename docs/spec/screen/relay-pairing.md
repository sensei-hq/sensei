# 結 · Relay · Pairing

**Segment:** 05 · Relay (mobile companion)
**Route:** Relay iOS app · pairing / onboarding (no web route — phone app)
**Source mockup:** [`lib/relay/relay.jsx`](../../mockups/Sensei/lib/relay/relay.jsx) → `RelayPairing`
**Data:** greenfield — the encrypted onboarding round-trip between phone and coordinator. Proposed: phone `POST /api/relay/pairing/start` → `{ code: "729416", expires_at }` (a 6-digit short code + a per-session keypair); the machine's `sensei relay pair` reads the code back, completes the key exchange, and the coordinator posts pairing-complete → phone advances to [Security](relay-security.md). The phone polls/streams `GET /api/relay/pairing/status` for `waiting_for → paired`.
**App file:** _greenfield — mobile app not built_
**Daemon files:** _greenfield — coordinator + relay transport not built · CLI `sensei relay pair` unbuilt_
**Status:** greenfield (Relay backend unbuilt) — see [architecture/relay](../../architecture/relay.md)

## Purpose

The very first moment: the user has installed the phone app and needs to
bind it to their Mac — securely, and with the reassurance that **nothing has
left their machine yet**. The phone shows a **6-digit code**; the user runs
one command on the Mac — **`$ sensei relay pair`** — which reads the code back
and completes the encrypted key exchange. The screen makes the round-trip
legible and calm: the code, the exact CLI line, a promise ("Nothing leaves
your Mac until it matches this code"), and a live **"Waiting for
{machine}…"** pulse until the handshake lands. It is the trust-establishing
front door; when it completes, the user drops into [Security](relay-security.md)
to grant scoped permissions.

## Data invariants

- The **6-digit code** is generated by the phone's pairing start and is the
  shared secret the human carries to the Mac. It is short-lived (has an
  `expires_at`) and single-use. The mockup shows `7 2 9 4 1 6`.
- The pairing is an **encrypted key exchange**, not a bearer code: the code
  authenticates the round-trip, but the actual channel keys are established
  between coordinator and phone (R6). The code alone grants nothing without
  the machine-side `sensei relay pair` completing the handshake.
- **ZERO-KNOWLEDGE from the first second:** the on-screen promise — "Nothing
  leaves your Mac until it matches this code" — is literal. No status, code,
  or file data crosses the relay before pairing completes; the phone is
  waiting, not receiving.
- The **exact CLI command** is shown verbatim: `$ sensei relay pair`. This
  mirrors the machine-side moment and must match the real CLI (greenfield —
  the CLI is unbuilt; keep this string in sync when it lands).
- The **waiting state** is live: "Waiting for {machine}…" with a pulsing
  indicator, driven by the pairing status stream. On `paired`, the screen
  advances to [Security](relay-security.md) to grant permissions.
- The `{machine}` name in the waiting line is the machine the coordinator
  reports once it initiates the pair — before that it may be a generic
  "your Mac".

## Done gate

The pairing screen shows a short-lived, single-use 6-digit code, the exact
`$ sensei relay pair` CLI line to run on the Mac, and a live "Waiting for
{machine}…" pulse driven by the pairing status stream — under a literal
promise that nothing leaves the Mac until the code matches. On handshake
completion the encrypted channel keys are established (not just a code
accepted) and the screen advances to [Security](relay-security.md) for
permission granting.

## Wrong gate

- **The code alone establishes the channel** (bearer-token pairing) with no
  key exchange — the code must authenticate a round-trip, not *be* the key (R6).
- **Status or any data flows before pairing completes**, contradicting
  "Nothing leaves your Mac until it matches this code" (R5).
- **The CLI string drifts from the real command** once `sensei relay pair`
  ships — the on-screen line must match what the user actually types.
- **The waiting state is fake** (a static "Waiting…" that never reflects the
  real handshake), so a stuck pair looks identical to a working one.
- **The code never expires / is reusable**, weakening the pairing secret.
- **Completion doesn't advance to permission granting** — the user is paired
  but never told what the phone is allowed to do, skipping the R6 permission step.
