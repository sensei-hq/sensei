# Relay P4 — prod activation runbook

P4 shipped on `develop` and released as **v0.4.0** to `main`; the code is live, but
the **prod cloud config** below must be applied for Web Push + client-direct
realtime to work in production. Assessed 2026-07-18: `wrangler` is **not** authed to
the prod CF account, and the prod DB password isn't wired locally (only the Supabase
CLI is *linked* to project `lagwuqrtshjtlcuvjfnd` / sensei-hq). So these are for
**Jerry to run** (or grant access + I'll run them). Nothing here is destructive to
data; step 3 changes the prod **security model** (RLS) and step 4 enables realtime —
do them in this order.

## ⚠ Ordering constraint (security)
Run **step 3 (RLS + grants) BEFORE step 4 (realtime publication).** If the relay
tables are in the `supabase_realtime` publication but lack RLS, realtime would (once
the `authenticated` SELECT grant lands) broadcast rows to clients. In practice
`authenticated` has *no* grant on the relay tables until step 3, so step-4-first is
merely non-functional (permission denied), not a leak — but keep the order anyway so
prod is never in a half-configured window.

## Step 1 — prod VAPID keypair + Worker secret (Web Push)
The prod VAPID **private key must be generated by you** (it's a prod signing secret —
I deliberately did NOT generate or handle it). One-time:
```bash
cd /Users/Jerry/Developer/sensei-hq/sensei/dojo
wrangler login                      # authenticates to the prod CF account
# generate a prod VAPID keypair (P-256) — keep the private key OFF disk/git:
node -e 'const {webcrypto:c}=require("crypto");(async()=>{const k=await c.subtle.generateKey({name:"ECDSA",namedCurve:"P-256"},true,["sign","verify"]);const pub=Buffer.from(await c.subtle.exportKey("raw",k.publicKey)).toString("base64url");const jwk=await c.subtle.exportKey("jwk",k.privateKey);console.log("PUBLIC_VAPID_KEY (public, set as a Worker var):\n"+pub+"\n\nVAPID private d (feed to `wrangler secret put VAPID_PRIVATE_KEY`):\n"+jwk.d)})()'
wrangler secret put VAPID_PRIVATE_KEY   # paste the `d` value above
```
(This matches the P4.3/P4.4 dev setup: the sender reads `VAPID_PRIVATE_KEY` +
`VAPID_SUBJECT` via `$env/dynamic/private`; the client reads `PUBLIC_VAPID_KEY`.)

## Step 3 — deploy the dojo schema to prod (ships relay RLS + grants)
The relay RLS (`enable row level security` + own-rows SELECT policies) + the
`grant select to authenticated` live in the **dbd-managed** relay DDL
(`database/ddl/table/dojo/relay_{sessions,segments,inbox}.ddl`) — they ship with a
normal dojo-schema deploy. Against the **prod** dojo Postgres (needs the prod
`DATABASE_URL` with the DB password):
```bash
cd /Users/Jerry/Developer/sensei-hq/sensei/database
DATABASE_URL="postgres://postgres:<PROD_DB_PASSWORD>@db.lagwuqrtshjtlcuvjfnd.supabase.co:5432/postgres" \
  dbd deploy --scope dojo -e prod     # (or the repo's standard prod dojo deploy path)
```
Idempotent (policies are `drop policy if exists` → `create policy`); safe to re-run.

## Step 5 — validate (read-only)
Confirm the four invariants on prod (read-only — do NOT run the harness's seeding
transaction against prod):
```sql
-- RLS enabled on all three relay tables (expect 3):
select count(*) from pg_class c join pg_namespace n on n.oid=c.relnamespace
  where n.nspname='dojo' and c.relrowsecurity and c.relname in ('relay_sessions','relay_segments','relay_inbox');
-- exactly the SELECT policies (expect 3):
select count(*) from pg_policies where schemaname='dojo'
  and tablename in ('relay_sessions','relay_segments','relay_inbox');
-- authenticated is SELECT-only, no I/U/D (expect 0):
select count(*) from information_schema.role_table_grants
  where grantee='authenticated' and table_schema='dojo'
  and table_name in ('relay_sessions','relay_segments','relay_inbox')
  and privilege_type in ('INSERT','UPDATE','DELETE');
-- relay tables in the realtime publication (expect 3):
select count(*) from pg_publication_tables where pubname='supabase_realtime'
  and schemaname='dojo' and tablename in ('relay_sessions','relay_segments','relay_inbox');
```
`scripts/relay-rls-check.sh` runs all of these locally; point its `DBURL` at prod for
the publication/RLS-enabled/grant checks (the member-sees-own / non-member-none
assertions need its seed fixture, so run those against a staging DB, not prod).
