# Phases 1-3 plan (P1 MVP → P2 relay → P3 analytics/insights/guidance)

(setup/config, observatory, project window, governance/relay, analytics,
DB data, mock gaps). Phases 4-6 are sketched for context and sequencing only —
detailed story breakdown starts at P4 in a later pass.

All current work is on `develop`, unmerged to `main` (confirmed: 48 commits
ahead of `origin/main`, 0 behind). Nothing in this plan changes that policy —
merges to `main` happen when a phase is stable per project CLAUDE.md.

## 6. Budget / execution notes

- **Prefer local models for daemon inference during execution + verification.**
  Route classification, signal derivation, insight-copy generation, and
  verification-support inference through the sensei gateway → embedded
  gemma/ollama chain wherever the task doesn't need frontier reasoning. Reserve
  cloud/paid models for judgment-heavy steps (code review, architecture
  decisions, ambiguous classification). This matches the existing
  `insight-copy` pipeline pattern (gemma4 primary, cache+fallback) and the
  gateway's local-first routing philosophy.
- **Worktree isolation for parallel story builds.** Stories in the same phase
  that touch disjoint files (e.g., P1-S6 through P1-S11, each a different
  project-window tab) can build in parallel git worktrees off `develop`, merging
  back into `develop` per-story once each passes its own zero-errors gate. Do
  not parallelize stories with a direct dependency edge (e.g., P1-S5 must land
  and be verified before any of P1-S6–S14 branch).
- **Two-account alternation for churn.** For long autonomous runs (per
  `feedback_autonomous_no_premature_stop` — don't idle awaiting steer), the
  user can alternate between two accounts to keep throughput up across
  API/usage limits during heavy multi-day story batches (P1's 20 stories, P2's
  7, P3's 10). Batch verification checkpoints (Playwright + DB check per story)
  so a handoff between accounts doesn't lose state — each story's verification
  step is self-contained and re-runnable.
- **Zero-errors-policy is non-negotiable per story.** Per project CLAUDE.md, no
  commit without running `zero-errors-policy`; TDD required for every
  needs-build story above. Verify-only stories still require a real
  Playwright/DB check — "done after coding" is not acceptable per the same
  policy.
- **Sequencing discipline.** P1-S5 (project window bug) gates almost the
  entire P1 project-window verification set — fix it first, before spending
  time verifying tabs that can't currently be reliably opened to test. P2's
  prod-activation stories (S4, S5) are explicitly Jerry-gated per existing
  backlog language — do not activate without sign-off even if code is ready.
