# Metric explainability — generation models (decision record)

_Status: current as of the v0.7.5 metrics batch. Referenceable if we later want
to change **when** the per-session observation is generated._

The metric detail experience has **two** LLM-authored, human-readable surfaces.
They are generated by **different** models on purpose. Both route through the
shared `insight_copy` pipeline (voice charter + parse/validate + 60s breaker +
durable `sensei.insight_copy` cache keyed on `(kind, facts_hash)`) — no new
tables, no new gateway paths.

Guiding principle (from the product owner): _"if the value does not change, why
should the explanation/observation associated with it change — the LLM copy is
the reason for the computed value, making it explainable."_ Both surfaces honor
this; they differ only in **when** the copy is produced.

## 1. Per-datapoint EXPLAINER — `InsightKind::MetricDayExplainer`

- **What:** one line explaining WHY a given day's metric value is what it is
  (project × metric × day, daily grain). The companion to each point on the trend.
- **When generated:** **at compute time, together with the value.** A shared
  enrichment runs in the metric `compute()` dispatcher right after a group's
  computer writes its daily `project_metrics` rows, and merges the line into
  `project_metrics.props.explainer`.
- **Regeneration rule:** the `insight_copy` facts **include the value** (value /
  prev_value / delta). So an **unchanged value → identical `facts_hash` → cache
  hit → no model call, identical text**; a **changed value → new hash →
  regenerate**. Because the backfill only computes **missing** days (planner
  `plan_days` = data − covered + trailing window + today), each day is explained
  once when its value is first computed; a trailing/forced recompute only
  regenerates when the value actually moved.
- **Where:** `analysis/metric_day_explainer.rs` (producer), enrichment wired into
  `tasks/handlers/metrics/mod.rs::compute()`, surfaced by the series read
  (`props->>'explainer'` per daily point).

## 2. Per-session per-metric OBSERVATION — `InsightKind::SessionMetricObservation`

- **What:** one line saying what a specific session contributed to a specific
  metric, shown in the datapoint → sessions drill-down.
- **When generated:** **lazily, on first drill-down view** (via `copy_or_warm` —
  the fallback shows immediately, the model copy warms off-wire for the next load).
- **Regeneration rule:** keyed by the session's **immutable** facts (outcome, ftr,
  corrections, turns, task, summary — a session is analyzed once and does not
  change). So it is generated once per viewed `(session, metric)` and is a cache
  hit forever after; an unchanged session **never** regenerates it. This satisfies
  the guiding principle — it just reaches the cache the first time a human looks,
  rather than at compute time.
- **Where:** `analysis/session_metric_note.rs` (producer), attached per session in
  the drill-down handler `api/handlers/metrics.rs`. Committed in `c4c90a2c`.

## Why they differ

- The explainer is **value-scoped** — it is literally the reason for a computed
  value, so it is produced with the value.
- The observation is **session-scoped** with an **immutable** input, and it is a
  drill-down detail (only meaningful when someone opens that day). Generating it
  lazily-once avoids generating an observation for every `(session, metric)` pair
  that no one ever views, while still never regenerating unchanged copy.

## If we want to move the observation to compute/analysis time

Reference point for a future change (to make it symmetric with the explainer):

- Generate it in the **session analyzer enrichment** (`analyze::enrich_session`),
  alongside `session_retro::generate_session_summary`, for each metric relevant to
  the session — awaiting `generate_and_cache(SessionMetricObservation, …)` so the
  copy is warm the moment the session is analyzed, before any drill-down.
- **Cost trade-off to weigh:** that is `N_metrics × sessions` model calls at
  analysis time (many never viewed) vs. today's lazy `1 call per viewed
  (session, metric)`. The drill-down handler could then drop the warm-on-miss and
  become a pure cache read.
- No storage change either way — same `insight_copy` kind + cache; only the
  **trigger** moves from read-time to analysis-time.
