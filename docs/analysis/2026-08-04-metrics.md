# Metrics & Agentic Behavior — Deep Analysis

_2026-08-04 · grounded in the live daemon DB (`sensei` on Postgres :5432)_

## What this is

The original version of this doc was a list of felt observations — babysitting,
degradation, amnesia, productivity, roadblocks, quality, plan/spec depth — plus ideas
for metrics beyond FTR. This revision keeps every one of those themes and puts a number
on it, using the data sensei has already collected about its own use.

**Method.** Twelve parallel analyst passes queried the live daemon DB and the on-disk
Claude Code transcripts. Every figure below is reproducible with SQL shown in the
[`2026-08-04-deep-dive/`](2026-08-04-deep-dive/) appendix; the headline numbers were
independently re-run against live data on 2026-08-04. Where the data contradicts the
original hunch, that is called out.

**The corpus.** 69 analyzed sessions (2026-07-06 → 2026-08-04), 1,762 turns, 131,692
assistant events, 9 autonomous runs, 476,988 code-graph nodes / 1,974,162 edges,
3.0 M indexing task-executions, 943 detected patterns, 1,478 recommendations, 11 durable
memories. FTR (first-time-right) sits at **46/68 = 67.6%**.

it collects.** Detection outruns consolidation (943 patterns → 11 memories → 1 correction
row); collection outruns measurement (exact tokens parsed then dropped; `success` never
written). Almost every fix below is "connect the last mile of a pipeline that already
exists," not "build something new."

# Part I — Agentic execution failures

## 1. Babysitting & Roadblocks (autonomy)

> **Original note.** "When a long plan is created … the runs do not continue
> autonomously. Every few minutes a summary is surfaced with a rhetorical question…
> Agentic execution does not resume when a limit is reached."

**What the data shows.**
- Of 9 autonomous runs: 5 done, 3 crashed, 1 failed. **All 4 non-done runs died at
  `recovery_attempts=3`** with `detail = "exhausted bounded recovery"`. These are not
  code crashes — the watchdog's fixed 3-nudge budget ran out and the run was declared
  dead.
- The daemon *has* a full limit-reset resume vocabulary — `runs.paused_until`,
  `pause_reason`, a `paused_on_limit` run-event, a `pause_run` MCP tool — and it has
  fired **exactly once in 800 run-events**, and that once was a `_verify_ pause smoke
  test`.
- The resume that *does* work is a hand-authored `/loop … so it survives usage limits`
  re-armed via `ScheduleWakeup` — 256 wakes confined to **2 sessions**, living entirely
  in the assistant-hook layer, writing nothing to `activity.runs`. **sensei has two
  disconnected autonomy runtimes and neither is complete.**
- Babysitting, quantified: **Stop events per UserPromptSubmit = 0.96** — the agent halts
  roughly once per human turn. 80% of Notifications (1,133/1,424) are the rhetorical
  "Claude is waiting for your input," versus 276 genuine "needs your permission" gates.

**Root cause.** Bounded recovery is the wrong policy for the two things that actually
stop a long run — a usage limit and a pending question. Both are *waits*, not *failures*,
but the watchdog counts them against a death budget. Meanwhile the real resume mechanism
lives in the prompt layer where the daemon can't see or manage it.

**Recommendations.**
1. **(P0)** Wire limit-reset resume into the daemon and route `/loop` through it: on a
   usage limit set `runs.status='paused'`, `paused_until=reset_time`, emit
   `paused_on_limit`, register a daemon-side wake, resume from
   `current_phase/current_feature`. Collapses the two runtimes into one.
2. **(P0)** Classify a stall before spending recovery budget: limit/permission/question
   → pause (unbounded, resume on trigger), not a nudge against the cap. Removes the
   false "crash" that killed 4/9 runs.
3. **(P1)** Replace the silent 3-nudge cap with a visible **autonomy budget**
   (turns/tokens/wall-clock/nudges) surfaced in the run view; emit a decision event when
   nearly spent instead of dying.
4. **(P1)** In autonomous mode, suppress rhetorical continue-prompts — proceed and log
   the decision to `run_events`; reserve Stop/Notification for real gates.

## 2. Degradation over run length

> **Original note.** "The longer the run the higher chance of deviation. Every execution
> seems to deliberately leave out one 'honest' caveat…"

**What the data shows.**
- Corrected-outcome rate is a clean **dose-response on session length**:
  `≤5 turns → 0%`, `6–15 → 11%`, `16–40 → 50%`, `41–80 → 83%`, `≥81 → 100%`.
  `corr(turns, corrections) = 0.854`; `corr(turns, ftr) = −0.580`. Corrected sessions run
  **6.8×** longer than completed ones (69.9 vs 10.3 turns). Every one of the 8 longest
  sessions is corrected *and* `ftr=false`.
- **The naive hypothesis is false, and that matters.** Flagged corrections
  (`is_correction`) cluster in the *first* half of long sessions (2.76% vs 1.22%). Late-run
  degradation is real but **silent**: it shows up as **effort decay** (tool-calls/turn
  peaks mid-session at 40.3, collapses to 25.7 in the final quintile; linear slope −13.4
  across a long run) and as **hedge sediment** ("for now", "placeholder", "would need
  to…"), whose count correlates with length at `r=0.897` and runs 1.6× denser in corrected
  sessions. Any correction/FTR dashboard therefore *under-counts exactly the phase that
  degrades most*.

**Root cause.** Context saturation plus a closure incentive. The agent is at full grip in
the middle and lossy at the end; the "honest caveat" is the visible residue of deferring
work to hit a stopping point. This is the behavioral twin of the mandatory *"never
fabricate on a failure path"* rule — a hedge is an un-materialized failure.

**Recommendations.**
1. **(P0)** Late-run verification pass: when a session crosses the ~16-turn inflection,
   inject a definition-of-done checkpoint that re-reads the spec, diffs it against what
   was built, and forces resolution of every open hedge before "complete."
2. **(P0)** **Caveat→task conversion**: classify genuine deferrals in
   `transcript_turns.assistant_text` and materialize each as a `drift_items` row or
   follow-up task. A hedge becomes tracked work, not lost intent.
3. **(P1)** Scheduled re-anchoring every ~15 turns (re-inject plan + acceptance criteria +
   top enforced memories via `context_pack`), logged as a `run_event` so its effect on the
   decay slope is measurable.

## 3. Amnesia (durable memory)

> **Original note.** "Planner reporting one 'honest' caveat that it cannot drive e2e tests
> on tauri app … same issue surfacing, without even consulting what is available."

**What the data shows.**
- **11 durable memories** stand against 943 patterns + 1,478 recommendations + 1,947 drift
  items + 88 reasoning traces. **8 of the 11 have never been recalled.** Memory *write*
  tools were invoked **8 times** in 131,692 events. All 11 are `type=convention` with NULL
  `spine_slot` — the richer memory grades (decision/pattern/preference/continuity/question)
  and the durable-context pinning machinery are built and entirely unused.
- The Tauri confabulation is real and self-admitted: the agent claimed it "can't visually
  verify" 9 times while browser/Playwright tools were invoked **1,003 times across 18
  sessions** — including a transcript turn where it wrote *"there IS a Playwright + Tauri
  e2e harness, and I've wrongly claimed can't visually verify repeatedly. That's a real
  error on my part, not a one-off."*
- The consolidation pipeline is stalled end-to-end: `inference.corrections` has **1 row**,
  and it is telemetry garbage (a mangled tool-notification dump). All 88 reasoning traces
  reach a consensus; **0** propose an action. `memory_loads.session_id` is NULL on all 24
  rows, so recall can't even be attributed to a session.

**Root cause.** The promotion path — from repeated pattern/correction to durable,
recallable memory — never fires, and nothing forces a capability lookup before a negative
claim. Knowledge is produced in bulk and discarded in bulk.

**Recommendations.**
1. **(P0)** Scheduled **memory-consolidation sweep**: promote patterns with
   `instance_count ≥ 3` and repeated high-rework recommendations into `sensei.memories`
   with the right type + `spine_slot`; seed corrections from the 38 real
   `turns.is_correction=true` rows, not the notification scraper.
2. **(P0)** **Recall-before-"I can't" guard**: intercept negative capability claims
   (cannot/unable + verify/e2e/test/tauri) and block them until a registry lookup
   (`assistant_tools`/`project_commands`) confirms no matching tool exists.
3. **(P1)** Restore `memory_loads` session linkage and increment
   `reinforced_count`/`violated_count` on use, so "did re-anchoring help?" becomes
   answerable — and surface a capability/harness registry at plan time.

## 4. Quality, Rework & Duplication

> **Original note.** "Code quality and maintainability are generally non-goals for the
> agents, so there tends to be a lot of code duplication and redundancy."

**What the data shows.**
- **92.3%** of edits are re-edits: 11,025 of 11,947 edits across 922 files are beyond the
  first write. **39.4%** of files are reworked across *more than one session* (the fix
  didn't stick). One file — `crates/senseid/src/db/pg_store.rs` — absorbed **301 edits**,
  203 of them in sessions *after* the one that first churned it. The top 10% of files
  absorb 32.8% of all re-edits.
- Duplication is live and detectable: the `get_duplicates` MCP tool returns 50 pairs at
  ≥0.92 similarity; `design-canvas.jsx` exists as **9 file copies**; `validateRequestBody`
  recurs across 37 files. sensei ships a working semantic duplicate detector **and it never
  runs at write time.**
- No deterministic quality signal is stored anywhere (complexity/coverage/lint/duplication
  columns are absent or unfed). sensei **dogfoods worst**: it has the most rework (410
  files) and the lowest FTR (43%) of any project; `dbd` runs 90% FTR with 43 rework files.
  Rework density and FTR move together.

**Root cause.** Quality is absent from the agent objective *and* there is no deterministic
scanner in the loop, so nothing rewards not-duplicating and nothing measures the drift.

**Recommendations.**
1. **(P0)** **Duplication guard in the write path** — on `PreToolUse` Write/Edit, look up
   new symbols against `sensei.nodes` + `get_duplicates` and soft-block re-implementations,
   discriminating new vs pre-existing duplicates (the user's exact ask).
2. **(P0)** Inject the top rework hotspots into session-start context so agents know which
   files are churn hotspots *before* editing them.
3. **(P1)** A `quality-scan-and-resolve` skill that runs a deterministic scanner
   (`qlty.sh`/`scc`/linters) at session start **and** end and persists a `quality_delta`
   into a new `activity.quality_snapshots` table — the missing deterministic anchor.

## 5. Regression & Churn (new lifecycle themes)

> **Added by request.** "regression and churn are other issues in lifecycle … graph used
> to work earlier … somewhere during various fixes the structure broke."

**Churn — a self-inflicted, datable regression.**
- The single largest daemon workload is **inert**: 92.1% of 924,709 `process_file`
  executions produced **zero** graph changes.
- It began the exact day the D2 version-rescan feature shipped (commit `2f6f1de9`,
  2026-07-12), which forces a full re-scan of every root on any daemon version bump.
  During active development the version bumps constantly, so `process_file` stepped from
  **4,038 → 34,828 executions/day (8.6×)** and `scan_root` from 9 → 5,059/week.
- That amplification lands on an incomplete binary filter (`classifiers.rs` omits `.p12`,
  `.epub`, `.lockb`, `.psd`, `.npz`, …), so **71% of all indexing work — 652,154
  executions on 1,218 binary blobs (535×/file)** — is spent re-opening files that can never
  yield a node. Churn is Pareto-extreme: the busiest 20% of files are 94% of the work.

**Regression proper — real, smaller, and invisible to FTR.**
- Doc-drift is 14% unresolved (273/1,947) but sharply **bimodal by repo** (torii 97.9%,
  alert-platform 100%, gateway 96% vs rokkit 3%, website 0%). The `drift_items` table is
  insert-only (1,947 rows for 487 distinct pairs), so re-breaks and mean-time-to-resolution
  aren't tracked. One doc broke→current **15×**.
- Reopened work is structurally invisible to FTR because FTR is a per-session snapshot:
  `senseid/src/db` was corrected in **3 separate sessions over 25 days**; two crashed runs
  re-attempted the *same* failing `plan_ref`.

**Root cause.** FTR measures a moment; regression and churn are cross-time phenomena that
no current metric or table window can see. And the largest "regression" is an accidental
one — a rescan trigger that turned indexing into a treadmill.

**Recommendations.**
1. **(P0)** Complete the binary filter (+ unit test) and move the binary check to the
   *enqueue* site so a skipped file never becomes a `task_executions` row. ~71% work cut.
2. **(P0)** Debounce version-rescan — gate the full re-walk on minor/major bumps or an
   explicit flag/DDL-version diff, not every patch. Reverts the 8.6× step.
3. **(P1)** Convert `drift_items` to **upsert** on `(doc_node_id, code_node_id)` with a
   maintained `resolved_at` + `break_count`, so re-breaks and MTTR become countable; add a
   `module_stability` rollup (completed-then-corrected sessions per module) and a
   run-regression guard that blocks silent re-attempts of a crashed `plan_ref`.
4. **(P2)** A **Lifecycle/Health** screen (Churn · Regression · Run-health), with any
   day-over-day FTR-drop alert gated below ~10 sessions/day to kill low-N noise.

> The code-graph half of this regression — why Atlas renders "scattered circles" — is a
> product-surface issue and lives in
> [Observations §1](2026-08-04-Observations.md#1-the-atlas-code-graph-regression) and
> deep-dive [10](2026-08-04-deep-dive/10-graph-indexing-regression.md).

## 6. Plan/Spec depth vs implementation

> **Original note.** "English language depth of plan and spec seems good, however
> implementation usually does not match and takes more effort in course correction."

This is the **composition** of §1–§5, and the data lets us name the seam. Plans are prose;
execution is unmeasured against them. The `runs` schema models features and phases
correctly, but **89% of the 800 run-events are undifferentiated housekeeping heartbeats** —
there is no `deviation` event that diffs executed `current_feature` against the
`plan_graph`. So a spec can be deep and the run can still wander, and nothing notices until
a human does (the 0.96 Stop/turn rate). Combined with silent late-run degradation (§2) and
dead memory (§3), "depth in, drift out" is the expected outcome, not a surprise.

**Recommendation (P1).** A **plan-adherence check**: at each `phase_done`, diff the
executed feature set against `runs.plan_graph` and emit a measurable `deviation` event.
Depth is only worth what execution preserves — so measure the preservation.

# Part II — Measurement

## 7. Productivity / Velocity

> **Original note.** "Purely lines of code does not make sense … N features × complexity /
> time."

The instinct to avoid LOC is correct, and the data shows why more strongly than expected:
**volume is inverted as a productivity signal.** 8 of the top-10 sessions by tool-calls are
corrected/`ftr=false`; corrected sessions average 2,405 tool-calls / 366 edits / 977 wall-
clock minutes versus 364 / 65 / 179 for completed ones. A LOC-or-edit leaderboard ranks the
worst work first.

The `N features × complexity / time` formula is buildable but needs three inputs sensei
doesn't yet capture:
- **N features** — the `runs` feature/phase model exists but only 9 runs used it; the 69
  interactive sessions carry no work-item structure. Derive WorkItems from the 459
  `TaskCreate` / 876 `TaskUpdate` MCP events already flowing, or promote the run model to
  sessions.
- **Complexity** — `nodes.degree` is NULL on all 476,988 nodes (the obvious centrality
  signal is unpopulated) and 63% of nodes are `const` noise. Weight by node **kind** and
  populate `degree` during the existing `resolve_edges` pass.
- **Delta** — no session→graph join exists. Add a per-session `graph_delta` (nodes/edges
  added, computed from the Edit/Write file list).

**The metric to actually report:** *Effective Velocity = Σ(complexity-weighted graph-delta
over completed sessions) / active-time*, shown **beside the Rework Ratio** (currently 0.76).
Never report raw volume alone — it points the wrong way.

## 8. FTR is good — but blind on four axes

FTR works (67.6%, and the original doc is right to keep it). But it is a per-session boolean
and is therefore blind to: **cost** (see §Token below), **model** (`model` 0/69 —
no per-model FTR possible), **the late-run phase** (§2 — silent degradation never becomes a
correction), and **cross-time regression** (§5). The companions that close those blind spots
are defined in the [metrics-catalog](2026-08-04-metrics-catalog.md).

## 9. Cost — and the "discard this work" hazard

> **Original note.** "One of the options provided is 'discard this work.' This is a very
> dangerous option and seems wasteful … would it put in the best effort?"

The cost data makes this concrete. sessions are token-blind at the DB layer (`tokens` 0/69),
but the **exact** per-message usage is already on disk in the Claude Code transcripts the
daemon parser opens — it just drops it (the `TranscriptTurn` struct has no usage field).
Recovering it for 58/67 linked sessions yields **30.5 B tokens, ~$64.8 k equivalent cost**,
and the punchline sensei is built to deliver but currently can't: **non-first-time-right
sessions cost 4.7× more than completed ones** ($2,411 vs $512), and 9 of the 12 costliest
sessions are corrected.

Against that, offering a blanket "discard this work" is not just demoralizing — it is
**expensive by construction** (discarding a corrected session is a ~$2.4 k write-off) and it
teaches the model that output is disposable, which undercuts the very best-effort the user
worries about. Prefer **salvage over discard**: checkpoint, extract the reusable delta, and
convert open hedges to tasks (§2) rather than dropping the whole session. Reserve true
discard for genuinely unsalvageable work, and show its cost when offered.

**Recommendation (P0).** Capture real usage from transcripts (below), price it via a
`gateway.model_prices` table (there is no cost table anywhere today; do not hardcode rates,
and fail closed on a price miss per the money-facing rule), and surface *cost/FTR* and
*cost-of-rework* tiles. See [token model](2026-08-04-metrics-catalog.md#token--cost-model).

# Part III — New metrics

The full catalog — every proposed metric with formula, source column, cadence, and current
data gap, plus a measurability matrix and the token model — is in
**[2026-08-04-metrics-catalog.md](2026-08-04-metrics-catalog.md)**. The families:

- **Outcome** — FTR, Rework Ratio, Regression Rate, Cross-session reopen rate.
- **Cost/effort** — tokens/session, cost/feature, cost-of-rework, cache-hit ratio.
- **Velocity** — complexity-weighted graph-delta / active-time; feature completion rate.
- **Quality** — duplication ratio, churn rate, churn concentration, drift MTTR, quality-delta.
- **Autonomy** — run completion rate, resume-success rate, interruption rate, autonomy ratio.
- **Knowledge** — memory-promotion rate, recall-hit rate, repeat-mistake rate.
- **Tool/content utility** — outcome-based utility score, unused-tool count, registry coverage.

Everything here rests on the mandatory rule *"measure, then keep what helps."* The first job
is not new metrics — it is filling the empty columns
([instrumentation gaps](2026-08-04-deep-dive/08-instrumentation-gaps.md)) so the metrics
that already have a home can finally be computed.
